### 왜 넓어지는가 — `prep_ab` §1-4 의 식이 그대로 맞습니다

### 원인 추적 — 임의로 넘어가지 않았습니다

세 가지를 실측했습니다.

1. **내 하네스는 결정적입니다** `[확인]`. 같은 조합을 GPU 로 두 번 돌려
   예측값이 **바이트 단위로 같습니다** (`np.array_equal` True, 최대 차 0.0).
   실행마다 흔들리는 종류가 아닙니다
2. **CPU 로 돌리면 6건 전부 재현됩니다** `[확인]`. 12개 CPTransformer 조합을
   CPU 로 다시 돌려 **12/12 통과**했습니다
3. **TF32 가 아닙니다** `[확인]`. `torch.backends.cuda.matmul.allow_tf32=False`,
   `float32_matmul_precision='highest'` 입니다

`[추론]` 따라서 원인은 **학습 조건과의 차이가 아니라 GPU 행렬곱 커널의 누산
순서**입니다. 부동소수점 덧셈이 결합법칙을 만족하지 않아 CPU 와 GPU 가
1e-5~1e-4 수준에서 갈리고, 어텐션이 있는 CPTransformer 에서만 그 차이가
Acc15 임계값을 넘나들 만큼 쌓입니다. MLP·CPMLP 는 선형·점별 연산뿐이라
GPU 에서도 그대로 재현됩니다.

`[미확인]` **학습 당시의 GPU 평가가 왜 CPU 값과 맞고 지금의 GPU 평가와는
어긋나는지**는 밝히지 못했습니다. 학습 때는 `accelerator.prepare` 가 감싼
모델·로더로 평가했고(`run_main.py:278`), 지금은 맨 모델로 평가합니다. 그
경로 차이가 커널 선택을 바꿨을 가능성이 있으나 확인하지 않았습니다.
**추측으로 채우지 않습니다.**

## 10. 지시에 없던 판단이 필요했던 사항

1. **`.build/` 진입점을 쓰지 않고 하네스 안에 같은 패치를 넣었습니다.**
   지시는 "필요한 수정은 `train/templates/entrypoint.py` 에만" 이라고 했는데,
   그 진입점은 `run_main.py` 를 통째로 실행하는 **학습 경로**입니다. 추론만
   하려면 그 경로에 들어가지 않는 편이 규칙 3("옵티마이저·역전파가 도는 코드
   경로에 들어가지 않는다")에 맞습니다. 대신 진입점 패치 2·3 과 **같은 코드**를
   `infer_cell_preds.py` 에 복제했습니다. 복제라 드리프트 위험이 있습니다 —
   공용 모듈로 뽑을지는 정해 주십시오.

2. **CPTransformer 정본을 CPU 결과로 삼았습니다.** GPU 6건이 기존 지표를
   재현하지 못했고 CPU 는 12/12 재현했습니다. 학습이 GPU 에서 돈 것을 생각하면
   GPU 를 정본으로 삼는 편이 자연스러워 보이지만, **재현되는 쪽을 택했습니다.**
   두 결과를 모두 남겼으니 뒤집으셔도 됩니다 (결론은 안 바뀝니다).

3. **원인 규명을 중간에 멈췄습니다.** §3 의 `[미확인]` — 학습 당시 GPU 평가가
   왜 지금 GPU 평가와 다른지까지는 파고들지 않았습니다. `accelerator.prepare`
   경로를 흉내 내 재평가하면 답이 나올 수 있으나, 그건 이번 지시 범위 밖으로
   보였습니다. **팔지 말지 정해 주십시오.**

4. **`.gitignore` 를 고치지 않았습니다.** §6 의 판단대로 커밋하는 편이 맞다고
   보았습니다. 제외하기로 하시면 규칙을 넣겠습니다.

5. **A/B 실험용 저장 경로를 "형식"까지만 만들었습니다.** 목적 2("A/B 에서 쓸
   저장 경로를 미리 만든다")를 `npz` + `cell_metrics.json` 두 층으로 잡았습니다.
   A/B 는 라벨이 바뀌므로 `refs` 가 조건마다 달라집니다 — 같은 파일에 두
   조건을 담을지, 조건별로 나눌지는 실험 설계에 달려 있어 정하지 않았습니다.

6. **MLP 의 CALB 셀별 오차를 §5 표에 넣지 않았습니다.** 지면 문제이고
   `cell_metrics.json` 에 전부 있습니다. 필요하면 표를 늘리겠습니다.
